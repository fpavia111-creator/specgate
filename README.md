## Quickstart

**Install** (Node.js ≥ 20):

```bash
npm install -g @kurtfrancisco/specgate   # or use npx @kurtfrancisco/specgate ...
```

**Claude Code**

```bash
claude mcp add specgate -- npx -y -p @kurtfrancisco/specgate@0.3.0 specgate-mcp
```

**Cursor** — add to `~/.cursor/mcp.json` (global) or `.cursor/mcp.json` (project). The same snippet works for Claude Desktop, VS Code and Windsurf:

```json
{ "mcpServers": { "specgate": { "command": "npx", "args": ["-y", "-p", "@kurtfrancisco/specgate@0.3.0", "specgate-mcp"] } } }
```

Restart the client and the tools appear. Full details below.


**From approved spec to tested code, with proof.** SpecGate adds two things teams need before they let AI agents write production code: a human sign-off on what will be built, and a record linking every test back to the requirement it proves.

It reads and writes the file formats of two open-source tools and works with or without them installed:

- **[OpenSpec](https://github.com/Fission-AI/OpenSpec)** writes the spec (proposal, requirements, scenarios).
- **[Superpowers](https://github.com/obra/superpowers)** plans and builds test-first from a clear spec.
- **SpecGate** is the gate in the middle and the audit trail at the end.

```
idea ──► spec (OpenSpec format) ──► SIGN-OFF ──► plan ──► TDD ──► GATE ──► merge
                                    specgate     specgate  tagged   specgate check
                                    approve      plan      tests    + verify-approvals
                                                                    + drift
```

## What you get

| | |
|---|---|
| **Sign-off** | `specgate approve` records the approver's name, email, optional role and note, the time, and a SHA-256 hash of the change's `proposal.md` and `specs/**/spec.md`. Edit those afterwards and the sign-off goes stale. Approvers are matched **by email only**; quorum is configurable. The MCP server has no approve tool, and the CLI refuses to approve in agent, CI or non-interactive contexts unless `--i-am-human` is passed. |
| **Review-backed sign-off (CI)** | `specgate verify-approvals` fails a pull request if any sign-off added in it isn't matched by an approving PR review from the GitHub login the *base branch's* `specgate.json` maps to that approver's email. |
| **Traceability** | Tests carry `@req <id>` tags. `specgate check` reads your JUnit XML and fails if a requirement has no test, a tagged test failed or didn't run, a result can't be attributed to one test unambiguously, a tag sits on a `describe` block, or a tag points at nothing. |
| **Drift** | Every sign-off stores a snapshot of each approved requirement. `specgate drift <change>` (and `check`) names the requirements changed, added or removed since sign-off and shows a line diff. With `--base REF`, code drift flags changed files in a capability's `areas` when no spec for that capability changed, and warns about unmapped code and untagged tests. |
| **Record** | `traceability.md`, `traceability.json` and `traceability.html` next to each change: approvers, every requirement, its tests and results, and any drift. |
| **Reports** | `check --format text\|json\|md\|html\|sarif\|github\|pr-comment`, plus `--sarif`, `--html`, `--summary` (PR comment) and `--annotations` (GitHub workflow commands) files. |
| **Test runners** | Jest, Vitest, node:test, pytest, Go (go-junit-report) and Java (Surefire, Gradle) JUnit output. A bundled node:test reporter (`specgate/junit-reporter`) records each test's file and line. |
| **Agent integration** | An MCP server confined to one repository, and a Claude Code plugin with four skills: `propose`, `plan`, `tdd`, `verify`. |
| **CI** | A GitHub Action (`action.yml`) and a workflow generated by `init`. |

## Quick start

```bash
npm install -D @kurtfrancisco/specgate
npx specgate init --approver lead@yourco.com     # config, folders, CI workflow, CODEOWNERS snippet
npx specgate new add-due-dates --capability todos
# write proposal.md and specs/todos/spec.md (or let the `propose` skill do it)
npx specgate validate add-due-dates
npx specgate approve add-due-dates --role "Product owner"   # a human runs this, at a terminal
npx specgate plan add-due-dates                              # refused until signed off
# implement test-first, tagging each test:  // @req todos/due-date#invalid-date-rejected
npx vitest run --reporter=junit --outputFile=reports/junit.xml
npx specgate check add-due-dates --junit reports/junit.xml --write
```

Already using OpenSpec? SpecGate reads your existing `openspec/` directory as is; `init` only creates files that are missing.

## Requirement ids

Each `### Requirement: Due date` in `openspec/.../specs/todos/spec.md` gets the id `todos/due-date`. Each `#### Scenario: Invalid date rejected` under it is `todos/due-date#invalid-date-rejected`. `specgate show <change>` lists them. Tag a test with either form, in a comment directly above the test (within 6 lines) or inside its title as `[@req …]`:

```ts
// @req todos/due-date#invalid-date-rejected
it("rejects an invalid due date", () => { ... });
```
```python
# @req todos/due-date
def test_due_date_round_trips(): ...
```

A tag counts only on a comment line (`//`, `#`, `/*`, `*`, `--`, `;`, `%`, `'`, `<!--`), in a trailing comment after code, or inside a test's title. Text that merely contains `@req` inside a string (a fixture, say) is ignored. Tag individual tests, not `describe`/`suite`/`context` blocks; a tag on a block is reported as a problem.

### How results are matched

A JUnit `<testcase>` counts for a tagged test only if its **full name** is the test's title (with or without an inline tag), or the title prefixed by `describe` titles from the same file (`suite > title`, `suite › title` or `suite title`). If the report records a location (a `file` attribute, or a path-like or dotted `classname` such as `test/a.test.ts`, `tests.test_todos` or `com.x.TodoTest`) it must point at the test's file. A name that merely *ends with* the title never matches. If several results with no location share the name, the test is reported as **ambiguous** and the gate fails; give it a unique name or use a reporter that records files. When the report also records a line, it is used to pick the exact test inside one file.

Runner notes:

| Runner | Command | Notes |
|---|---|---|
| node:test | `node --test --test-reporter=specgate/junit-reporter --test-reporter-destination=reports/junit.xml` | Use SpecGate's reporter: Node's built-in JUnit reporter records no file names, so same-named tests in different files would be ambiguous. |
| Vitest | `vitest run --reporter=junit --outputFile=reports/junit.xml` | File is recorded as the classname. |
| Jest | `jest --reporters=default --reporters=jest-junit` | Set `JEST_JUNIT_ADD_FILE_ATTRIBUTE=true` so results carry the file. |
| pytest | `pytest --junitxml=reports/junit.xml` | Module and class classnames are matched to the file. |
| Go | `go test -v ./... 2>&1 \| go-junit-report > reports/junit.xml` | The package path is matched to the test file's directory. |
| Java | Maven Surefire / Gradle JUnit XML | `com.acme.TodoTest` is matched to `…/com/acme/TodoTest.java`; Gradle's `name()` form is accepted. |

## Commands

| Command | Does |
|---|---|
| `init [--approver EMAIL]... [--required N]` | Create `specgate.json`, OpenSpec folders, `.github/workflows/specgate.yml`, `.github/CODEOWNERS.specgate`. `N` must be a whole number ≥ 1; approvers must be emails |
| `new <id> --capability C [--why TEXT]` | Scaffold a change (proposal, spec, tasks) |
| `list` | In-flight changes and their sign-off state |
| `show <id>` | Requirement and scenario ids to tag tests with |
| `validate [<id>]` | Spec format checks: SHALL/MUST, scenarios, duplicates, TODOs |
| `approve <id> [--as "Name <email>"] [--role R] [--note N] [--i-am-human]` | Record a sign-off (identity from git config by default) |
| `revoke <id> [--email EMAIL]` | Withdraw a sign-off |
| `status <id>` | Sign-off state (exit 0 only if approved) |
| `plan <id> [--force]` | Write a Superpowers-format, test-first `plan.md` (needs sign-off) |
| `check <id> \| --all [--junit F]... [--write] [--json] [--base REF] [--format F] [--out FILE] [--sarif FILE] [--html FILE] [--summary FILE] [--annotations FILE]` | The gate. Exit 1 on failure (including requirement drift, and code drift when `--base` is given) |
| `drift <id> [--base REF] [--json]` | Requirement-level drift since the last sign-off, with diffs. Exit 1 if drifted |
| `drift --base REF [--json]` | Code drift in the diff from `REF` (merge base) to the working tree. Exit 1 on code drift errors |
| `verify-approvals --base REF [--pr N] [--repo O/R] [--head SHA] [--reviews FILE]` | CI check of sign-offs against PR reviews. Reads `GITHUB_TOKEN`, `GITHUB_REPOSITORY` and `GITHUB_EVENT_PATH` when flags are omitted |

All commands accept `--root DIR`, and `--key value` or `--key=value`. Change ids must be lowercase kebab-case (`add-due-dates`). Exit codes: 0 pass, 1 gate failure, 2 usage or configuration error.

`--all` checks every in-flight change plus the living specs in `openspec/specs/`, so archived requirements stay covered by passing tests.

## Configuration (`specgate.json`)

Defaults (any key may be omitted; invalid values are an error, never silently ignored):

```json
{
  "openspecDir": "openspec",
  "testGlobs": ["**/*.test.*", "**/*.spec.*", "**/test_*.py", "**/*_test.py", "**/*_test.go", "**/test/**", "**/tests/**", "**/__tests__/**"],
  "ignoreGlobs": ["**/node_modules/**", "**/.git/**", "**/dist/**", "**/build/**", "**/.venv/**", "**/vendor/**"],
  "requiredApprovals": 1,
  "approvers": [],
  "requireScenarioCoverage": false,
  "github": { "approverLogins": {}, "requireReviewOnHead": false },
  "areas": {},
  "requireAreaCoverage": false
}
```

- `approvers`: email addresses. Empty means anyone may sign off.
- `requiredApprovals`: distinct approver emails needed.
- `requireScenarioCoverage`: demand a test per scenario, not just per requirement.
- `github.approverLogins`: maps approver email to GitHub login, e.g. `{ "lead@yourco.com": "lead-gh" }`, for `verify-approvals`.
- `github.requireReviewOnHead`: the approving review must be on the PR's latest commit.
- `areas`: maps a capability to the globs of the code it governs, e.g. `{ "todos": ["src/todos/**"] }`, for code drift.
- `requireAreaCoverage`: make changed code outside every area an error instead of a warning.

## Making sign-off trustworthy

`approvals.json` is a file in your repo, and anyone who can run the CLI or edit files can write to it. The agent-context check in `approve` (it refuses when stdin is not a terminal or a known agent/CI variable is set; piping the output is fine) is a speed bump, not a security boundary. What makes a sign-off mean something is CI:

1. Map each approver's email to their GitHub login under `github.approverLogins`.
2. Run `verify-approvals` on pull requests (the generated workflow and the Action both do). It compares `approvals.json` files with the base branch and requires each new sign-off to have an approving review from the mapped login. The mapping is read from the **base** branch, so a PR can't approve itself by editing it.
3. Make the SpecGate job a required status check, and merge `.github/CODEOWNERS.specgate` into `CODEOWNERS` with "Require review from Code Owners" turned on.

## GitHub Action

```yaml
on: [pull_request, pull_request_review]
permissions: { contents: read, pull-requests: read }
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - run: npm ci && npm test        # writes reports/junit.xml
      - uses: <owner>/specgate@v0.3.0
        id: specgate
        with:
          junit: reports/junit.xml
          drift: "true"
      # Optional: show findings in code scanning, and post the summary as a PR comment.
      - if: always()
        uses: github/codeql-action/upload-sarif@v3
        with: { sarif_file: specgate.sarif }
```

The step prints GitHub annotations for every finding and appends the PR-comment summary to the job summary. Its `summary-file` output (Markdown starting with `<!-- specgate:summary -->`) can be posted with any comment action; SpecGate itself never posts, so the job only needs read permissions (plus `security-events: write` if you upload SARIF).

Inputs: `junit` (space-separated paths, default `reports/junit.xml`), `change` (one change id; default all), `version` (exact `x.y.z`, default `0.3.0`), `verify-approvals` (default `"true"`; runs on `pull_request`/`pull_request_review` events), `drift` (default `"false"`; code drift against the PR base), `sarif` (default `specgate.sarif`; empty to skip), `github-token` (default `github.token`). Outputs: `summary-file`, `sarif-file`. Inputs reach the script only through environment variables and are validated.

## MCP server

```json
{ "mcpServers": { "specgate": { "command": "npx", "args": ["-y", "-p", "@kurtfrancisco/specgate@0.3.0", "specgate-mcp"] } } }
```

Tools: `list_changes`, `show_change`, `new_change`, `signoff_status`, `write_plan`, `check`, `drift`. The server is confined to `SPECGATE_ROOT` (or its working directory): a per-call `root` must be inside it, JUnit paths must be inside the root, and change ids must be slugs.

## Claude Code plugin

This package is a plugin (`.claude-plugin/plugin.json`, `skills/`, `.mcp.json`). The skills `specgate:propose`, `specgate:plan`, `specgate:tdd` and `specgate:verify` drive the flow. Generated plans also name Superpowers' `subagent-driven-development` and `executing-plans` skills, which can run them if Superpowers is installed.

## Development

The source is plain ES-module JavaScript in `src/`, compiled to `dist/` by TypeScript (`allowJs`).

```bash
npm install
npm test        # builds, runs 64 node:test tests with SpecGate's own reporter, then `npm run gate`
npm run gate    # SpecGate checks its own openspec/specs (23 requirements) against reports/junit.xml
```

SpecGate is specified in its own `openspec/specs/` (capabilities `signoff`, `gate`, `trace`, `drift`, `reports`, `integration`), every requirement there is covered by a tagged test, and `npm test` fails if any of them has no passing test.

## Upgrading from 0.2

- **Tags in strings no longer count.** A `@req` tag must be in a comment or a test title (see *Requirement ids*). Run `specgate check --all` after upgrading; a requirement that becomes `Untested` had a tag in a non-comment string.
- **`approvals.json`** entries now include a `snapshot` of the approved requirements. Existing 0.2 sign-offs stay valid; requirement-level drift detail needs a fresh sign-off.
- **`traceability.json`** gains `findings` and `drift`; existing fields are unchanged. `check --write` also writes `traceability.html`.
- **`approve`** no longer refuses just because stdout is piped; stdin must still be a terminal.
- **`package.json` now has `exports`**: `specgate/junit-reporter`, `specgate/dist/*`, `specgate/src/*` and `specgate/package.json` are importable.
- Action default version is `0.3.0`; new inputs `drift` and `sarif` default to off and `specgate.sarif`.
